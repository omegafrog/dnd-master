# Local Ollama operation

Copy `.env.local-ai.example` to `.env.local-ai`, then set `OLLAMA_MODEL_ROOT` to an existing canonical directory on `E:` or `F:`. Before startup, verify that the host directory is not a junction/reparse point and has at least 20 GB free. `docker compose ... config` and `docker inspect <ollama-container-id>` must show a `bind` mount from that exact canonical source to `/root/.ollama`; named volumes and other drives are rejected by the containerized metadata guard tests. Linux scripts treat the Windows source only as Compose metadata and access model files exclusively through `/root/.ollama`.

From the host, invoke Docker Compose only: `docker compose --env-file .env.local-ai -f compose.local-ai.yml up -d ollama`, then `docker compose --env-file .env.local-ai -f compose.local-ai.yml exec ollama sh /workspace/scripts/prepare-local-ai.sh`. The Linux script explicitly pulls the chat and embedding models inside the Ollama container. This is the only command that pulls models.

Run `docker compose --env-file .env.local-ai -f compose.local-ai.yml exec ollama sh /workspace/scripts/verify-local-ai.sh` to inspect the running Linux container, mount target, loopback topology, and already-installed models. It never pulls a model. Ollama is exposed only as `127.0.0.1:${LOCAL_AI_HOST_PORT:-11434}`; the Maven runner shares its network namespace and uses `http://localhost:11434`.

Run `docker compose --env-file .env.local-ai -f compose.local-ai.yml run --rm --entrypoint sh runner /workspace/scripts/benchmark-local-ai.sh` for the namespace-sharing Maven/Temurin 21 benchmark. It runs two warmups and five measured executions and prints p95 milliseconds. It intentionally logs only aggregate timings; prompts, raw responses, and secrets are not emitted. The required `LocalAiBenchmarkRouteTest` is supplied by the B4 live-E2E gate, so this command is not part of B3 verification.
