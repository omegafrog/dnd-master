# 전투 맵 격자·벽·문 검수 및 시야 개선 계획 초안

- 작성: 2026-09-08
- 상태: 조사 기반 제안. 제품 정책과 상세 설계 확정 전이며 구현 승인 계획이 아니다.
- 범위: 플레이 전 AI 탐지와 사용자 최종 검수, 격자·토큰 조작, 벽·문 충돌, 현재 시야와 탐험 기록.
- 조사 방법: 기존 지식 그래프로 관련 파일을 찾고 현재 소스를 확인했다. 외부 제품은 공식 도움말과 공개 개발 문서를 참고했다. 외부 제품을 직접 실행하거나 비공개 구현을 확인하지 않았다.

AI가 임의 이미지를 정확히 탐지한다는 근거는 위 사례에서 확인하지 않았다. AI 초벌 탐지와 사람 검수의 결합은 이번 제품의 제안이며, 대표 이미지로 정확도와 수정 시간을 측정해야 한다.

## 3. 사용자 흐름

맵 선택 → AI 초벌 탐지 → 격자 검수 → 벽·문 검수 → 시험 토큰으로 시야 확인 → 최종 승인 → 플레이에서 승인본 사용.

1. **AI 초벌 탐지**: 이미지 영역, 격자 기준점·크기, 벽 끝점, 문 후보를 제시한다. 각 후보에 원본 위치와 불확실한 이유를 표시한다. AI의 자체 확신 수치를 검증된 정확도로 취급하지 않는다.
2. **격자 검수**: 확대·이동, 기준 교차점 선택, 여러 칸에 걸친 크기 보정, 수치 입력을 함께 제공한다. 인쇄 격자가 없는 지도도 수동 지정 가능하다. 반복 수정과 실행 취소·다시 실행을 지원한다.
3. **벽·문 검수**: 선분 추가·끝점 이동·분할·삭제, 이어 그리기, 끝점 맞춤, 벽 일부를 문으로 변환. 격자에 맞추기를 해제해 비스듬한 벽도 지정한다.
4. **오류 확인**: 짧은 틈, 중복 경계, 문 위를 계속 막는 벽, 이미지 밖 좌표를 강조한다. 의도적인 통로까지 자동으로 막지 않는다.
5. **시야 시험**: 시험 토큰 이동과 문 열기·닫기로 차단을 확인한다. 시험 상태와 실제 문 상태·탐험 기록은 별도이며 저장 승인은 실제 탐험을 만들지 않는다.
6. **최종 승인**: 이미지와 격자·벽·문을 하나의 버전으로 고정한다. 변경하면 새 검수본이 된다. AI 재탐지는 별도 후보로 표시하고 사용자 수정분을 덮어쓰지 않는다.

탐지 실패 시 실패 사유와 해당 맵 재시도를 제공한다. 수동 편집으로 완료할 수 있으나 최종 검수는 생략하지 않는다. 벽 없는 야외 지도는 벽 0개를 명시적으로 승인할 수 있다.

## 4. 시야·안개·토큰 규칙 제안

| 영역 | 표시 | 공개 가능한 정보 |
| --- | --- | --- |
| 현재 토큰 시야 안 | 정상 색상 | 현재 관찰 가능하고 발견 조건을 충족한 지형·토큰 |
| 전에 보았지만 현재 시야 밖 | 회색조 지형 + 어두운 덮개 | 마지막으로 확인한 지형. 적의 현재 위치나 문 상태 변경은 공개하지 않음 |
| 한 번도 보지 못한 곳 | 불투명 안개 | 숨겨진 지형·토큰·문 정보 비공개 |

- 현재 시야 = 토큰 시야 범위 안에서 벽·닫힌 문에 가리지 않는 영역. 이동 충돌과 시야 충돌은 같은 경계를 사용하되 각 차단 속성을 따로 적용한다.
- 탐험 기록 = 이전 탐험 영역 ∪ 새로 확정된 현재 시야. 회색 영역 = 탐험 기록 − 현재 시야.
- 문 열림 → 해당 문의 시야·이동 차단 해제. 문 닫힘 → 다시 차단하되 이미 탐험한 지형은 회색으로 남긴다.
- 일반 이동은 서버가 승인한 경로에서 실제 통과한 시야를 기록한다. 순간이동은 도착점만 새로 계산한다. 미확정 드래그·취소·거절 경로는 기록하지 않는다.
- 토큰 크기·이동 경로 전체로 통과 가능 여부를 검사한다. 도착점만 검사하면 얇은 벽을 건너뛸 수 있다.
- 플레이어 토큰은 선택 테두리와 이동 가능 경로를 표시한다. 시야 밖 적의 실제 좌표·이름·상태를 화면이나 응답에 넣지 않는다.
- 기존 `Last Seen Token`(마지막 목격 토큰)은 합의된 최근 1턴 표시를 유지한다. 과거 위치임을 명시하고 실제 이동을 추적하지 않는다. 지형의 영구 탐험 기록과 구분한다.
- 시야 밖 문은 마지막 관찰 상태를 보존하거나 현재 상태를 생략한다. 기존 서비스가 탐험한 칸의 문 최신 상태를 전달하는 부분은 수정 대상이다.
- AI의 정보 공개 제안은 발견 여부와 탐험 기록을 바꿀 수 있어도 물리적으로 가려진 영역을 현재 시야로 강제 전환하지 못하도록 기존 공개 경로를 검토한다.
- 서버가 공개 범위를 확정한다. 브라우저는 받은 공개 영역을 그린다. 검수용 전체 자료와 플레이용 응답을 구분한다.

## 5. 구현 방향과 순서

| 순서 | 변경 묶음 | 완료 기준 |
| --- | --- | --- |
| 1 | 이미지 기준 좌표, 선분 벽·문, 검수본·승인본 저장 | 격자 보정에도 이미지 위 벽 위치 유지. 재접속 후 초안 복원. 이전 버전 수정 요청 거절 |
| 2 | 기존 AI 이미지 연동 확장, 후보 검증과 재탐지 | 후보와 원본 대응 확인. 실패 후 수동 완료 가능. 늦게 도착한 AI 응답이 수정본을 덮어쓰지 않음 |
| 3 | 플레이 전 편집 화면, 시험 토큰, 최종 승인 | 격자·벽·문 모두 반복 편집 가능. 시험 이동이 실제 탐험에 반영되지 않음 |
| 4 | 서버 시야·이동 충돌과 문 상태 갱신 | 대각선·모서리·문 개폐·큰 토큰·경로 통과 사례 통과 |
| 5 | 회색조 탐험 표시와 토큰 화면 개선 | 현재·과거·미탐험 구분, 마지막 목격 표시, 숨겨진 정보 비노출 |
| 6 | 기존 데이터 전환과 전체 흐름 검증 | 기존 모험 재개 가능, 승인본 참조 고정, 재진입·재접속 후 탐험 유지 |

맵 서비스가 기하 정보·승인본·문 상태·시야 계산을 소유한다. AI 서비스는 후보만 제공한다. 모험 서비스는 승인본 참조와 이동·문 상호작용의 게임 규칙 검증을 조정한다. 웹 화면은 편집 및 공개 상태 표시를 맡는다.

좌표는 이미지 기준으로 저장하고 격자 이동 좌표와의 변환을 명시한다. 기존 격자 보정처럼 칸 개수 비율만으로 벽·문·토큰을 옮기지 않는다. 초기에는 정사각 격자와 직선 선분을 우선하며 이미지 회전·왜곡 보정, 육각 격자, 높이·다층, 복잡한 광원은 후속 후보로 둔다.

전체 칸마다 모든 벽을 검사하지 않도록 가까운 경계만 찾는 공간 색인과 시야 결과 재사용을 검토한다. 초기 구현 후보는 끝점 방향의 광선과 선분 교차로 시야 경계를 만들고 범위로 자르는 방식이다. 공선·접점·교차점 오차를 검증한 뒤 필요하면 회전 순회 방식으로 최적화한다. 서버 판단과 화면에 표시한 시야 경계는 같은 결과를 사용한다.

기존 칸 장애물을 선분으로 바꿀 때는 칸 외곽선을 임시 경계로 만들 수 있지만 원래 벽 위치를 복원했다고 간주하지 않는다. 기존 진행 중 모험은 기존 자료로 재개하고, 새 준비 과정에서 변환 후보를 검수한다. 진행 중 맵의 강제 변환이나 탐험 초기화는 하지 않는다.

## 6. 검증 계획

- 기하: 직선·대각선·ㄱ자 복도·모서리 접촉·겹치는 선분·작은 틈·열린 문 위 잔여 벽·좁은 문과 큰 토큰.
- 안개: 처음 진입, 이동 후 회색 전환, 문 개폐, 일반 이동과 순간이동 차이, 재접속과 맵 재진입, 마지막 목격 만료.
- 편집: 격자 보정 전후 동일 이미지 위치 유지, 사용자 수정 보존, 승인 이후 변경, 중복 승인, 동시 수정, 탐지 실패와 재시도.
- 공개 정보: 시야 밖 적 이동과 문 개폐가 화면·API 응답·이벤트에 노출되지 않음. 검수용 숨김 자료도 별도 확인.
- 대표 자료: 격자 있는 지도, 없는 지도, 흐린 스캔, 비스듬한 벽, 문이 많은 던전. AI 후보 오류 수와 사람이 승인까지 수정한 시간을 기록해 수동 작업과 비교.
- 성능: 맵 크기·벽 수·시야 토큰 수별 서버 계산 및 화면 갱신 시간을 측정한다. 성능 목표 수치는 대표 자료와 실행 환경을 정한 뒤 확정한다.
- 실제 흐름: WSL의 `src/start-dev.sh`로 실행 후 서버 상태 확인 → 업로드·검수·승인·플레이·문 개폐·재접속 브라우저 테스트.

## 7. 확정할 제품 선택

1. **검수 중 비밀 노출 범위**: 1인 플레이 사용자가 전체 지형을 검수하면 지형을 미리 알게 된다. 전체 지형 허용 및 적·함정·비밀문 정보 숨김을 우선 제안하되 사용자 답변 전 미확정이다. 원본 이미지 자체에 비밀 표식이 있으면 표시 데이터 필터만으로 숨길 수 없으므로 검수용 이미지 처리까지 필요하다.
2. **시야 공유 범위**: 현재는 플레이어 종류 토큰 위치를 사용한다. 초기에는 기존 범위를 유지하고 AI 동료 시야 합산 여부를 별도로 확정할 것을 제안한다.
3. **플레이 중 새로 생성되는 지도**: 시작 전 존재하지 않는 지도를 사전 검수할 수는 없다. 해당 지도 첫 진입 직전에 동일 검수 단계를 거치는 방안을 제안한다.
4. **시야 범위와 조명**: 토큰별 룰북 근거를 우선한다. 초기 조명 모델을 전체 밝음으로 제한할지, 암시야·광원까지 함께 구현할지 확정해야 한다.

위 선택이 남아 있으므로 본 문서는 승인된 제품·아키텍처 명세나 확정된 개발 일정으로 취급하지 않는다.
