# Product Spec: 캐릭터 생성 설정 검토 UX 및 룰북 스키마 단일화

## 1. Problem and Context

현재 화면은 룰북의 기본 캐릭터 생성 구조와 스토리북에서 추출한 시나리오 전용 제안을 하나의 편집 화면으로 보여준다. 사용자는 룰북 기본 규칙을 직접 채우는 것인지, 스토리북 제안을 검토하는 것인지 구분하기 어렵다.

이 화면의 목적은 캐릭터를 생성하는 것이 아니다. 선택한 룰북이 제공하는 기본 캐릭터 생성 스키마를 보여주고, 스토리북에서 추가로 발견된 항목이 있는지 확인한 뒤 필요한 제안만 캐릭터 생성 설정에 포함할지 결정하는 것이다.

## 2. Goals and Desired Outcomes

- 룰북 기본 스키마와 스토리북 추가 제안을 서로 다른 영역에서 보여준다.
- 룰북 기본 스키마는 읽기 전용 참고 정보로 인식되게 한다.
- 스토리북 제안마다 내용, 출처, 원문 근거와 결정 상태를 보여준다.
- 사용자가 제안을 `사용하기` 또는 `제외하기`로 결정할 수 있게 한다.
- 스토리북 제안이 없을 때도 정상적인 빈 상태를 보여준다.
- 사용자가 현재 상태와 다음 행동을 즉시 이해하도록 한다.
- 모든 제안 결정이 끝난 뒤에만 캐릭터 생성에 사용할 설정을 확정할 수 있게 한다.
- 룰북별 캐릭터 생성 기본 스키마와 모든 선택지를 하나의 버전 관리되는 백엔드 카탈로그로 관리한다.
- 캐릭터 생성 설정 검토와 실제 캐릭터 생성이 같은 백엔드 카탈로그/API를 사용하도록 한다.
- 프런트엔드에 판본별 룰북 선택지·설명·규칙 근거를 하드코딩하지 않는다.

## 3. Users and Actors

- **Solo Player**: 룰북 기본 스키마를 확인하고 스토리북 제안을 결정하는 사용자.
- **Scenario Preparation**: 룰북과 스토리북을 분석해 기본 스키마와 추가 제안을 제공하는 시스템.
- **Rulebook Catalog**: 판본별 기본 캐릭터 생성 스키마를 제공하는 시스템.
- **Rulebook Character Catalog**: 룰북 판본별 캐릭터 생성 필드, 선택지, 선택지 설명, 자동 계산 규칙, 출처 근거를 포함하는 백엔드 관리 데이터.
- **Catalog Revision**: 특정 룰북 판본의 불변 캐릭터 생성 카탈로그 버전. 모험 준비와 캐릭터 생성에서 동일 버전을 참조한다.

## 4. Ubiquitous Language and Terminology

- **룰북 기본 스키마**: 선택한 판본이 기본적으로 제공하는 캐릭터 생성 항목과 선택지. 항상 캐릭터 생성에 포함되며 사용자가 이 화면에서 수정하지 않는다.
- **스토리북 제안**: 스토리북에서 발견된 시나리오 전용 항목 또는 제한. 사용자가 사용하기로 결정하기 전에는 캐릭터 생성에 포함되지 않는다.
- **제안 결정**: 제안을 `미결정`, `사용하기`, `제외하기` 중 하나로 분류하는 행위.
- **사용할 설정 확정**: 룰북 기본 스키마와 사용하기로 결정한 스토리북 제안을 캐릭터 생성에 적용할 설정으로 확정하는 행위.
- **캐릭터 생성**: 확정된 설정을 사용해 실제 캐릭터의 이름, 종족, 클래스, 능력치 등을 입력하는 다음 단계.

## 5. Core Use Cases

### UC-01 룰북 기본 스키마 확인

사용자는 선택한 판본, 기본 항목의 범주, 주요 선택지를 읽기 전용으로 확인한다. 기본 스키마는 별도 입력 폼처럼 보이지 않아야 한다.

### UC-02 스토리북 제안 확인

사용자는 스토리북에서 추출된 추가 항목을 문서별 또는 범주별 카드로 확인한다. 각 카드에는 제안 내용, 출처 파일, 추출 요약, 원문 근거와 현재 결정 상태가 표시된다.

### UC-03 스토리북 제안 결정

사용자는 각 제안에 대해 `사용하기` 또는 `제외하기`를 선택한다. 결정하지 않은 제안은 미결정 상태로 남고 설정 확정을 막는다.

### UC-04 추가 제안 없음 확인

스토리북 분석 결과 추가할 항목이 없으면 시스템은 “추가할 내용이 없습니다”를 표시하고 분석 대상과 완료 상태를 함께 알려준다.

### UC-05 설정 확정

모든 제안이 결정되면 사용자는 룰북 기본 스키마와 사용하기로 한 제안의 요약을 확인하고 `캐릭터 생성에 사용할 설정 확정`을 실행한다.

### UC-06 캐릭터 생성 진입

설정 확정 후에만 캐릭터 생성 화면으로 이동한다. 이 화면에서는 실제 캐릭터 값을 입력한다.

### UC-07 룰북 기본 스키마와 선택지 제공

시스템은 선택한 룰북 판본의 카탈로그 리비전에서 기본 필드, 선택이 필요한 항목의 전체 선택지, 선택지 설명, 자동 계산 항목과 룰북 근거를 불러온다. 검토 화면은 이를 읽기 전용으로 보여주고, 캐릭터 생성 화면은 같은 응답을 사용해 입력 선택지를 구성한다.

## 6. Business Rules and Invariants

- BR-01: 룰북 기본 스키마는 항상 최종 캐릭터 생성 설정에 포함된다.
- BR-02: 룰북 기본 스키마는 검토 화면에서 읽기 전용으로 표시한다.
- BR-03: 스토리북 제안은 사용자가 `사용하기`로 결정한 경우에만 최종 설정에 포함한다.
- BR-04: `제외하기`로 결정한 제안은 최종 설정에 포함하지 않는다.
- BR-05: 미결정 제안이 하나라도 있으면 설정을 확정할 수 없다.
- BR-06: 출처 또는 원문 근거가 없는 제안은 사용하기로 결정할 수 없다.
- BR-07: 스토리북 제안이 없다는 것은 오류가 아니며 정상적인 완료 상태다.
- BR-08: 설정 확정 전에는 실제 캐릭터 생성 단계로 이동할 수 없다.
- BR-09: 설정 확정 후에는 적용된 룰북 기본 스키마와 사용 제안의 집합이 게시 결과와 일치해야 한다.
- BR-10: 내부 ID, enum, `Blueprint`, `PUBLISHED` 같은 구현 용어는 사용자 화면에 노출하지 않는다.
- BR-11: 룰북 기본 스키마와 선택지는 선택된 카탈로그 리비전에서만 제공하며, 프런트엔드 정적 목록을 권위 있는 데이터로 사용하지 않는다.
- BR-12: 캐릭터 생성 설정 검토와 실제 캐릭터 생성은 동일한 룰북 판본·카탈로그 리비전을 사용한다.
- BR-13: 선택지가 필요한 항목은 전체 선택지와 설명을 제공해야 하며, 자동 계산 항목은 선택 항목으로 표시하지 않는다.
- BR-14: 카탈로그 데이터에는 각 필드·선택지의 룰북 출처와 근거를 포함한다.
- BR-15: 카탈로그 리비전은 게시 후 변경하지 않으며, 수정은 새 리비전으로 처리한다.

## 7. States and State Transitions

### 7.1 Review State

`LOADING → READY → DECISIONS_REQUIRED → CONFIRMABLE → CONFIRMED`

예외 상태는 `LOADING → FAILED`이며, 재시도할 수 있다.

- `READY`: 기본 스키마와 제안 목록을 불러온 상태.
- `DECISIONS_REQUIRED`: 미결정 제안이 하나 이상 있는 상태.
- `CONFIRMABLE`: 모든 제안이 결정되어 확정할 수 있는 상태.
- `CONFIRMED`: 캐릭터 생성에 사용할 설정이 확정된 상태.

### 7.2 Proposal Decision

`UNDECIDED → APPLIED | EXCLUDED`

근거가 없거나 추출이 불완전하면 `NEEDS_EVIDENCE` 상태로 표시하며 `APPLIED`로 전환할 수 없다.

## 8. Failures, Exceptions, and Boundary Conditions

- 기본 스키마를 불러오지 못하면 제안 카드를 표시하지 않고 재시도 방법을 제공한다.
- 스토리북 분석이 실패하면 대상 문서와 실패 원인을 표시한다.
- 스토리북 제안이 없으면 빈 상태를 성공으로 표시한다.
- 제안에 근거가 없으면 사용하기를 비활성화하고 확인 필요 사유를 표시한다.
- 확정 중 최신 revision과 충돌하면 최신 결과를 다시 불러오고 사용자의 결정이 사라질 수 있음을 안내한다.
- 긴 원문 근거와 선택지 설명은 접을 수 있어야 한다.
- 좁은 화면에서는 기본 스키마, 제안, 확정 요약을 세로로 배치한다.
- 룰북 카탈로그 리비전을 불러오지 못하면 검토와 캐릭터 생성을 진행시키지 않고 재시도 가능한 오류를 표시한다.
- API 응답의 카탈로그 판본 또는 리비전이 세션에 고정된 값과 다르면 캐릭터 생성 입력을 차단한다.

## 9. Inputs and Outputs

### Inputs

- 룰북 판본과 기본 스키마
- 스토리북 분석 결과
- 제안별 사용/제외 결정
- 설정 확정 요청

### Outputs

- 읽기 전용 룰북 기본 스키마 요약
- 제안별 내용, 출처, 근거, 결정 상태
- 사용하기로 결정된 제안 목록
- 설정 확정 결과와 캐릭터 생성 진입
- 선택된 룰북 카탈로그 리비전과 그 안의 기본 스키마·선택지·근거

## 10. Scope and Non-goals

### Scope

- 검토 화면의 정보 구조와 용어 개선
- 룰북 기본 스키마와 스토리북 제안의 시각적·의미적 분리
- 제안별 사용/제외 결정과 확정 요약
- 제안 없음·분석 실패·근거 부족 상태 표현

### Non-goals

- 이 화면에서 실제 캐릭터 값을 입력하는 흐름
- 룰북 원문 또는 스토리북 추출 알고리즘 변경
- 캐릭터 시트 계산 규칙 변경
- 실제 캐릭터 생성 화면 재설계
- 룰북 PDF를 런타임에 프런트엔드가 직접 읽거나 선택지를 자체 추출하는 기능

## 11. Priorities and Trade-offs

1. P0: 기본 스키마와 제안 분리
2. P0: 제안별 사용/제외 결정과 미결정 차단
3. P0: 제안 없음·실패·근거 부족 상태 표현
4. P1: 기본 스키마 범주 요약과 제안 문서별 그룹화
5. P1: 적용 결과 요약과 접근성·반응형 개선
6. P0: 검토 화면과 캐릭터 생성 화면의 룰북 카탈로그/API 단일화

기본 스키마를 완전히 펼쳐 보여주는 것보다, 사용자가 “무엇이 기본이고 무엇을 결정해야 하는지” 이해하는 것을 우선한다.

## 12. Success Conditions and Acceptance Criteria

- AC-01: 사용자는 화면 진입 후 이 화면이 실제 캐릭터 입력 화면이 아님을 알 수 있다.
- AC-02: 룰북 기본 스키마와 스토리북 제안이 별도 영역으로 표시된다.
- AC-03: 룰북 기본 스키마의 항목은 읽기 전용으로 보인다.
- AC-04: 각 제안에 내용, 출처 파일, 원문 근거, 결정 상태가 표시된다.
- AC-05: 사용자는 각 제안을 사용하기 또는 제외하기로 결정할 수 있다.
- AC-06: 미결정 제안이 있으면 설정 확정 버튼이 비활성화된다.
- AC-07: 제안이 없으면 성공적인 빈 상태가 표시된다.
- AC-08: 근거 없는 제안은 사용하기로 결정할 수 없다.
- AC-09: 확정 결과에는 룰북 기본 스키마와 사용하기로 한 제안만 포함된다.
- AC-10: 확정 전에는 캐릭터 생성 화면으로 이동할 수 없다.
- AC-11: 내부 UUID와 구현 상태명이 사용자 화면에 표시되지 않는다.
- AC-12: 선택된 판본의 카탈로그 리비전이 기본 스키마, 선택지, 설명, 자동 계산 여부, 룰북 근거를 API로 제공한다.
- AC-13: 검토 화면과 캐릭터 생성 화면이 동일한 카탈로그 리비전의 선택지를 표시한다.
- AC-14: 프런트엔드 소스에 판본별 룰북 선택지와 설명의 별도 권위 목록이 존재하지 않는다.
- AC-15: 카탈로그 리비전이 없거나 불일치하면 사용자가 캐릭터 생성으로 진행할 수 없다.
