# 공용 룰북 전처리 페이지 관리자 검토 보충 구조 계약

이 계약은 [#376](https://github.com/omegafrog/dnd-master/issues/376)에 한정한다. 기존 [구조 명세](architecture-spec.md)의 Document Knowledge 소유권과 공용 목록 선행 준비 경계를 따른다.

- 기존 `RulebookCatalogBackofficeController`의 세션 기반 관리자 검사를 재사용한다. 목록 등록 ID로 문서를 찾아 실제 공용 목록 등록·내부 소유자·`RULEBOOK` 자료형을 함께 검증한 뒤 조회·재시도 경로로 넘긴다. 개인 문서의 소유자 경로는 그대로 둔다.
- 기존 등록 저장소, `RulebookPipelineApplicationService.retryPages`, 전처리 프로세스와 후보/페이지 상태를 재사용한다. 새 서비스, 저장소 또는 새 사용자 업로드 여정은 만들지 않는다.
- 요청은 현재 후보 추출 버전과 페이지별 영역/후보 번호, 원본 PDF 대조 확인을 명시한다. 서버는 등록 건·페이지·현재 후보와 정확히 일치하는지 확인한 뒤 처리한다. 전처리 경계에서도 후보 번호를 실제 재추출 후보 범위에 맞춰 확인한다.
- 후보를 선택한 영역에 대해서만 수동 확인 근거를 보존하고 열 판정의 통계 신뢰도 실패를 해결한다. 다른 축의 신뢰도와 글자·기하·근거·순서의 오류는 기존 검사로 계속 차단한다. 자동 신뢰도 정책 값은 변경하지 않는다.
- 재시도 결과의 페이지 상태에는 확인자와 선택 후보·원본 후보 버전을 추적할 수 있게 하고, 원본 파일 바이트·해시 및 기존 저장 버전 식별자는 바꾸지 않는다. 오류가 남은 페이지는 `NEEDS_REVIEW`로 반환한다.

기존 조회 → 선택 → 재시도 흐름과 저장 경계만 고치므로 새 흐름/구조 다이어그램은 필요하지 않다.
