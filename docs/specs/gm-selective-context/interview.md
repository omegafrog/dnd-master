# 모험 진행 컨텍스트 개선 — 합의 및 남은 확인

이 문서는 대화 중 확정된 요구사항과 확인 결과를 보존한다. 완료된 제품·아키텍처 명세가 아니다.

## 사용자와 합의한 요구사항

- 모험 시작 이후 턴 진행을 개선한다. 기존 대화 요약, 장기 기록, 서사 상태와 각 데이터 소유권을 재사용한다.
- 기본 컨텍스트를 자동 준비하고, GM이 자신의 실행 과정에서 추가로 필요한 정보의 대상·종류·범위를 결정한다. 이를 결정하기 위한 별도 LLM 판단 단계는 추가하지 않는다.
- 기존 시츄에이션 선택 구현을 재사용한다. 선택된 시츄에이션은 매 턴 기본 컨텍스트에 포함한다. 목표·도전·조건·진행 상태는 최신 저장 상태에서 읽고, 관련 과거 사건·관계·약속은 장기 기록으로 연결한다.
- 장면 개요에는 숨겨진 사건·단서의 존재와 확인 조건을 GM 전용 정보로 포함한다. GM의 내부 조회 권한과 플레이어에게 공개할 수 있는 정보는 구분한다.
- 추가 조회는 정본 게임 상태와 구조화된 시나리오를 우선하고, 해결되지 않는 내용은 고정된 문서 범위에서 검색한다. 기존 다섯 프롬프트 구역과 비동기 대화 압축을 재사용한다.
- 필수 근거 조회 실패 시 판정·비밀 공개 및 턴 확정을 보류하고 재시도한다. 단순 묘사에 필요한 정보가 없으면 확인된 정보만으로 진행한다.
- 전체 턴 완료 목표는 5초 이내다. 서버 행동 요청 접수부터 기본 정보 준비, GM 판단, 추가 조회, 엔진 검증, 상태 저장, 최종 응답 전달까지 포함한다. 플레이어의 주사위 입력 대기는 제외한다.
- 5초를 초과하더라도 같은 요청에서 완료까지 대기한다. 5초는 강제 중단 시간이 아니다. 초과한 턴을 성공 지연 측정에서 제외하거나 오류 응답으로 대체해 목표를 충족했다고 판정하지 않는다.

## 코드에서 확인한 현재 상태

기준: 작업 브랜치 `spec/gm-selective-context`, 기준 커밋 `caa31a6277a61bfcefb06dc0491c52866e7fb4b1`.

- `StoryRuntimeRules.apply`는 선택된 시츄에이션의 활성화·종료·무효화를 검증한다. `StoryRuntimeApplicationService.apply`는 검증 결과를 모험에 저장한다. 실제 GM 호출에서 선택 제안이 연결되는지는 추가 확인 중이다.
- `RuntimeTurnApplicationService`의 일반 턴 입력 구성은 현재 상황, 장기 기록, 시나리오·지도 자료를 전달하지만 선택된 시츄에이션 식별자와 연결된 목표·조건을 명시적으로 전달하지 않는다.
- `RuntimeGmPromptComposer.selectedLongTermFacts`는 플레이어 공개 가능 기록을 최신 버전 순으로 선택한다. 선택된 시츄에이션과의 관련성을 기준으로 선택하지 않는다.
- 로컬에는 `e61225cf939e165801fd349c34fc5e1790bae352`가 존재한다. 별도 턴 지연 개선 브랜치의 커밋으로, 현재 작업 기준에 포함된 것으로 간주하지 않는다.

## 추가 조사 결과

- 사용자 PC의 Codex 실행에는 `search_rules`라는 룰북 검색 도구가 이미 있다. `LocalCodexAiExecutionPort.McpRelayServer`와 `CodexWebSocketAgent.requestRagSearch`가 같은 GM 실행 중 요청을 중계한다. 일반 공식 GM 도구 목록과 별도의 경로이므로 새 조회 기능 설계에서 이 경로를 함께 검토해야 한다.
- `RuntimeFactLookupService.lookup`는 정본에서 답을 찾지 못하면 `ScenarioModelLookupAgentPort`를 호출한다. HTTP 구현은 `internal/gm/scenario-lookup`으로 요청한다. 사전 근거 판단 외에 이 사전 조회의 모델 호출도 제거·재사용 범위 검토 대상이다.
- 기존 룰북 조회 도구만으로 게임 상태·시나리오·장기 기억의 통합 조회가 제공되지는 않는다.
- `GmCompletionRouter.completeWithResolution`는 `codex-cli` 경로에서만 조회 범위를 실행 요청에 전달한다. 다른 제공자도 같은 기능을 지원한다고 가정할 수 없다.
- `AgentWebSocketHandler`는 사용자·연결·활성 요청에 연결된 검색 범위를 확인한다. `HttpRagToolSearch`는 서버가 확정한 범위를 복사하고 질의만 추가해 `internal/v1/evidence-candidates/search`에 요청한다. 기존 읽기 전용 검색 중계를 재사용할 수 있지만, 모험 상태·기억 조회는 추가 연결이 필요하다.
- `TypedAgentContractController.scenarioLookup`는 실제 모델 호출로 잠긴 시나리오에서 답을 고른다. 따라서 사전 근거 판단만 제거하면 별도 사전 모델 호출이 남을 수 있다.
- 조회 중계의 현재 응답 대기 한도는 150초다. 이는 실제 측정 지연이 아니며, 이번 5초 성공 응답 목표를 달성했다는 근거가 될 수 없다.
- 코드 조사만 수행했다. 모델·검색·상태 저장을 합친 실행 시간은 아직 측정하지 않았다.

## 남은 확인 항목

- 제품 요구사항의 최종 누락 확인은 사용자 답변 “ㄴㄴ”로 완료했다.
- 실제 제공자별 GM 실행 중 조회 경로, 시츄에이션 선택 호출 연결, 공개 정보 전달 경계의 변경 범위.
- 반복적인 제공자·조회 장애의 최종 실패 및 재개 정책. 5초 초과 대기는 무한 재시도 승인으로 해석하지 않는다.
- 현재 지연 실측값, 시험 환경·동시 요청 수·모델 설정과 5초 목표의 검증 방법. 실측 전 달성을 주장하지 않는다.

## 제품 검토 현황

문제·목표·사용자·용어·핵심 흐름·정본 소유권·공개 규칙·입출력은 사용자 요청 및 후속 합의로 확인했다. 실패 처리의 기본 기준과 5초 초과 처리, 최종 누락 확인도 완료했다. 반복 장애는 기존 최종 오류 처리를 유지하고 무한 재시도를 추가하지 않는다. 제품 명세 본문과 UC-01·UC-02의 유스케이스·액티비티 원본 및 SVG를 작성했다. 로컬 렌더, 네 Markdown 링크와 비어 있지 않은 SVG, 명세와 흐름의 일치를 검토했다. 제품 단계 산출물은 완료됐으며 제공자별 적용 범위는 아키텍처 단계에서 확인 중이다.

## 재개 상태

- 사용량 제한 후 작업 상태를 확인했다. 제품 명세 본문은 존재하며 완료된 작성 작업을 반복하지 않았다.
- 다이어그램 작업을 동일 작업자가 재개해 완료했다. 선택적 근거 누락 시 진행, 필수 근거 누락 시 보류, 굴림 후 확정, 다음 턴과 비동기 압축의 독립 진행을 검토·수정했다.
- 제공자 적용 범위는 사용자 답변 “Codex부터 적용, 다른 제공자는 기존 방식 유지”로 확정했다. Codex의 기존 실행 중 조회 경로를 확장하며, 다른 제공자의 요청 구성·근거 확보·응답 처리는 기존 동작을 유지한다.
- 추가 조사에서는 시작 시 선택되는 시츄에이션과 현재 상황이 별도 값임을 확인했다. 일반 턴에서 시츄에이션 선택 제안을 생성·적용하는 운영 호출 연결은 찾지 못했다. 기존 선택·상태 변경 규칙의 존재만으로 전체 연결이 완성됐다고 판단하지 않는다.
- `system_targets_complete` 검사 결과는 pass다. 이는 목표 문서의 형식 검사이며 실제 5초 달성 증거는 아니다. 현재 지연과 동시 요청 수는 미확인으로 기록했다.

## Codex 적용 범위 확정 후 아키텍처 검토

아래는 구현 연결을 구체화하기 위한 검토안이며 완료된 아키텍처 명세가 아니다.

1. **기본 정보 준비**: 기존 모험 실행 서비스에서 같은 턴의 저장 버전을 기준으로 현재 상황, 선택된 시츄에이션, 해당 국면의 목표·확인 조건, 관련 기억을 조합한다. 시츄에이션 본문은 저장된 국면 자료의 정확한 버전으로 해석한다. 선택 식별자가 없으면 일반 플레이로 처리하고, 식별자가 있으나 대응 자료가 없으면 정상적인 부재와 구분한다.
2. **조회 실행**: Codex의 기존 도구 중계를 재사용한다. 서버가 인증된 사용자·모험·턴·자료 버전을 결정하고, GM은 필요한 대상·정보·범위만 요청한다. 모험 상태와 기억의 조회 책임은 기존 모험 실행 서비스에 둔다. 도구 중계에 별도 정본 저장소를 만들지 않는다.
3. **불필요한 선행 호출 제거**: Codex 턴의 근거 사전 판단과 모델을 사용하는 시나리오 사전 조회를 GM 자체 판단·선택적 조회로 대체한다. 다른 제공자의 기존 경로에는 이 변경을 적용하지 않는다.
4. **근거의 검증 연결**: `HttpTypedRuntimeGmAgentPort`는 현재 `context.evidencePack()`에서만 인용 키를 해석하고, 목록에 없는 판정 근거를 거절한다. 실행 중 조회 결과를 GM에게 주는 것만으로는 이 검증을 통과하지 못한다. 서버가 해당 실행에 실제 반환한 근거를 보존하고, 기존 검증이 확인할 수 있는 턴 근거 목록에 합치는 연결이 필요하다. GM이 반환한 출처 문자열만 신뢰하거나 인용 검증을 생략하지 않는다.
5. **기억 연결**: `LongTermAdventureFact`는 사건 식별자·출처 턴·관련 설명을 보유하며, `RuntimeAddedFact`가 확정 사실을 소유한다. 관련 기록 선택과 상세 조회는 이 연결을 유지하고, 시츄에이션의 현재 상태를 요약에 복제해 정본으로 사용하지 않는다. 현재 관련성을 나타내는 구조화된 연결이 부족한 경우의 선택 기준은 구현 계약에서 명시해야 한다.
6. **공개 경계**: GM 전용 조회 결과 전체를 플레이어 응답이나 대화 기록에 넣지 않는다. 공개 허가와 서술 검증을 거쳐 확정된 결과만 기존 저장 경로에 전달한다. 공개 가능 기록만 선택하는 기존 필터를 단순 제거하는 변경은 허용하지 않는다.
7. **지연 검증**: 준비·GM 실행·도구 조회·검증·저장·응답의 시간을 같은 턴으로 연결해 측정한다. 응답 후 압축은 별도 계측한다. 외부 모델 왕복 지연을 포함한 5초 목표의 충족 여부를 구현 후 판단한다.

### 기존 시츄에이션 선택 연결에서 발견한 차이

`StoryRuntimeState.start`와 `AdventureStartApplicationService`는 시작 시츄에이션을 선택해 저장한다. `StoryRuntimeRules`와 `StoryRuntimeApplicationService`에는 활성화·종료·무효화 규칙이 있다. 그러나 조사한 운영 코드에서는 일반 GM 턴이 `StoryRuntimeProposal`을 만들어 그 규칙에 전달하는 호출을 찾지 못했다. 따라서 현재 선택값을 기본 정보에 넣는 작업과, 이후 선택·종료 제안을 기존 규칙에 연결하는 작업은 구분해야 한다. 새 선택 판단 모델을 만들 필요는 없지만 일반 턴 연결의 보완 범위를 확인해야 한다.

사용자는 이 누락 연결을 이번 범위에 포함하는 것에 “ㅇㅋ”로 동의했다. 기존 선택 규칙을 재사용하고, 동일 GM 실행의 제안을 턴 검증·확정 과정에 연결한다. 조회 도구가 시츄에이션을 활성화하거나 종료해서는 안 된다.

### 시츄에이션 반영의 일관성

- GM에게 제공한 국면·시츄에이션의 버전과 실제 확정할 저장 버전이 같은지 검증한다.
- 시츄에이션 변경 제안은 판정·공개·현재 상황 변경과 같은 턴의 미확정 결과로 보존한다. 플레이어 굴림 대기 중에는 선택·종료를 먼저 저장하지 않는다.
- 기존 모험 저장 및 턴 복구 과정에서 확정한다. `StoryRuntimeApplicationService.apply`를 별도로 먼저 호출해 한 턴의 일부만 저장하는 방식은 피한다.
- 같은 턴을 재시도해도 시츄에이션의 활성화·종료가 중복 반영되지 않게 기존 제안 식별자·처리 이력과 턴 중복 방지 규칙을 유지한다.
- 시츄에이션이 종료되면 다음 턴 기본 정보에서 진행 중 항목으로 제외한다. 확정된 결과·약속·관계는 기존 대화와 장기 기록으로 이어진다.

## 아키텍처 문서 작성 및 검토 상태

- 제품 명세에 Codex 적용 범위와 일반 턴 시츄에이션 제안 연결을 반영했다. 다른 제공자는 기존 입력·근거·응답 경로를 유지한다.
- 아키텍처 명세 초안과 별도 클래스·실행 상태 다이어그램을 작성했다. 검토 과정에서 기억 소유권, 실행 중 조회 근거의 서버 전달 시점, 인용 검증 후 턴 보존 순서를 보완했다.
- 개념 검토에서는 사용자 합의와 새 충돌이 발견되지 않았다. 구체 계약의 최종 검토는 아직 완료로 표시하지 않는다. 실제 측정·구현 검증과 문서 형식 검사를 구분한다.
- 구현·테스트·5초 성능 측정은 실행하지 않았다. 문서와 다이어그램 수정만 수행했다.

## 기존 서술 전용 경계에 대한 사용자 정정

사용자는 “원래 설계에서는 \"봐도 되는 정보만 보고 서술하는 에이전트\"가 따로 서술만 담당했었는데”라고 기존 설계의 경계를 지적했다. 앞선 별도 서술 단계 신설 제안은 이 기존 경계를 놓친 제안이었다. 기존 공개 정보 전용 서술 경계를 재사용하는 것으로 설계를 바로잡는다.

- 기존 `runtime-reveal-filter/architecture-spec.md`의 4.1~4.3은 `RevealFilter`가 공개 가능한 결과를 `PlayerVisibleTurn`으로 만들고, `TurnWriterPort`가 이 입력만 받아 서술하도록 정한다. 내부 계획, 시나리오 정본, 검색 자료, 내부 판정 결과는 서술 담당자의 금지 입력이다.
- 실제 `ScenarioRuntimeWriterAdapter`는 공개 사실이 없으면 `narrationSeed`를 그대로 반환한다. 현재 일반 턴 구성에는 내부 `plan.narration()`을 이 입력으로 전달하는 경로가 있으며, 응답 재생성 경로에도 내부 서술을 직접 사용하는 분기가 있다. 경계 타입이 존재하는 것과 입력이 실제 공개 정보로 제한된 것은 구분한다.
- 이번 설계는 기존 공개 정보 전용 서술 경계를 활용하고 이 우회·전달 연결을 보완한다. GM의 비공개 판단·조회 대화·기억·서술 원문을 서술 담당자에게 전달하지 않는다. 장면 및 서사 문맥도 플레이어 공개 범위로 구성한다.
- 서술 단계는 엔진이 허가한 관찰 결과·이미 공개된 사실·이번 판정으로 공개되는 정보만 사용한다. 공개 여부를 확정하지 못한 정보는 제외하고, 필수 결과를 구성할 수 없으면 기존 보류·재시도 정책을 적용한다.
- 기존 서술 경계 재사용은 모델 호출이 실제 몇 번 발생하는지에 대한 증거가 아니다. 판단·조회·서술·검증·저장을 모두 포함한 5초 목표를 유지하고 실제 실행 경로에서 측정한다.
- 기존 공개 정보 전용 경계를 명시하고 내부 서술 전달·우회를 금지한 수정 계약을 검토했다. 비공개 서술 경계 이의는 설계 수준에서 해결됐으며, 구체 검토에서 남은 설계 이의는 없다. 실제 구현 누출 검증과 5초 성능 검증은 아직 수행하지 않았다.
