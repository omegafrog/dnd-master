# ADR-019: 공간 요소 준비의 소유 경계와 저장 계약

## 상태

Accepted

## 배경

Issue #327 구현에서 모험 준비, AI 배치 후보, 전투 지도 저장의 책임이 섞였다. 그 결과 다음 문제가 생겼다.

- 전투 지도 경계가 AI 후보 생성을 직접 호출할 수 있음
- 이미 준비된 지도라는 이유로 새 명령의 지문·기준 버전 검증을 건너뛸 수 있음
- 필수 준비 실패가 안전한 결과가 아니라 일반 예외로 노출될 수 있음
- 공간 요소의 종류별 지속·제거·중첩 정보가 저장되지 않을 수 있음
- 저장 구조와 실제 모험 시작부터 지도 저장까지의 검증 경계가 불명확함

Product Spec과 Architecture Spec은 이미 책임 경계를 정하고 있다. 이 ADR은 구현 blocker를 해소하기 위한 해석을 고정한다.

## 결정

### 1. 모험 준비가 배치 흐름을 소유한다

`adventure-service`의 Scenario Preparation이 다음 순서를 소유한다.

1. Adventure Story Plan과 구조화된 근거에서 배치 요구사항을 만든다.
2. AI Game Master에 후보를 제안하도록 요청한다.
3. 후보를 근거·칸·종류·필수 여부·시점·버전으로 검증한다.
4. 검증된 배치 묶음만 Combat Map의 내부 계약으로 전달한다.
5. 성공·선택 요소 경고·필수 요소 차단 결과를 받아 지도 활성화 여부를 결정한다.

Combat Map은 AI 호출 통로를 소유하거나 AI를 호출하지 않는다. Combat Map은 검증된 배치 묶음의 권위 있는 저장과 지도 활성화 조건만 소유한다.

새 업무 경계, 코드 모듈, 배포 서비스를 만들지 않는다. 기존 Adventure Runtime과 Combat Map 내부 패키지·호출 통로 경계가 가장 작고 충분한 경계다.

### 2. Combat Map은 검증된 배치 묶음만 원자적으로 저장한다

`SpatialFeatureApplicationService`는 Combat Map 내부 기능이다. 입력에는 다음이 반드시 포함된다.

- `commandId`: 중복 처리 기준이 되는 명령 식별자
- `fingerprint`: 요청의 안정적인 식별 정보와 검증된 배치 묶음을 합친 전체 지문
- `mapId`, `adventureId`, `ownerPlayerId`
- `expectedMapVersion`
- 근거가 연결된 공간 요소 묶음

Combat Map은 저장 직전에 소유권·기준 버전·배치 범위·근거 연결·명령 지문을 다시 검증한다. 지도·공간 요소·시야·준비 결과·명령 이력은 하나의 로컬 트랜잭션으로 저장한다.

AI 결과를 아직 다시 만들지 않은 응답 복구 조회는 예외적으로 요청의 안정적인 식별 정보만 전달한다. 이 정보는 모험·지도 정의·단계·상황 등 AI 호출 전에 이미 결정되는 값이며 `commandId`를 만드는 입력이다. Combat Map은 저장된 전체 지문이 이 안정적인 식별 정보로 시작하는지 확인한 뒤에만 잃어버린 응답을 재생한다. 이 조회는 새 배치를 승인하는 최종 저장이 아니며, 실제 준비 저장과 배치를 알고 있는 재처리 경로는 전체 지문 완전 일치만 허용한다.

### 3. 재시도와 차단 결과는 우회하지 않는다

- 같은 `commandId`와 같은 전체 `fingerprint`: 저장된 준비 결과를 그대로 반환한다.
- 같은 `commandId`와 다른 `fingerprint`: 명령 충돌을 명시적 409 결과로 반환한다.
- AI 호출 전 응답 복구는 같은 안정적인 요청 식별 정보가 저장된 전체 지문에 포함될 때만 허용하고, 다른 요청 식별 정보는 명령 충돌로 반환한다.
- `expectedMapVersion` 불일치: 버전 충돌을 명시적 409 결과로 반환한다.
- 저장된 `spatialPreparationBlocked=true`: 새 명령 검증 없이 `READY`로 반환하거나 활성화하지 않는다.
- 필수 준비 실패: 숨겨진 좌표·내부 실패 원인을 제외한 유형이 명확한 `BLOCKED` 결과를 반환한다.
- 선택 준비 실패: 요소를 저장하지 않고 내부 경고를 준비 결과에 남긴다.

호환 연결부가 남아도 위 계약을 우회할 수 없다. 기존 지도 조기 반환은 제거한다.

### 4. 근거는 문자열이 아니라 구조화된 사실로 전달한다

배치 요구사항은 단순한 근거 문자열을 권위 있는 사실로 취급하지 않는다. 각 요구사항은 최소한 다음 연결을 가진다.

- Scenario Package 또는 Story Plan의 버전
- Resolution Unit 또는 배치 요구사항 식별자
- 원문 위치 또는 원문 구간 식별자
- 허용된 칸 또는 칸 묶음
- 공간 요소 종류·필수 여부·생성 시점·생성 버전

AI는 이 사실을 바꿀 수 없다. AI 응답의 좌표가 구조화된 허용 칸과 일치하지 않으면 저장하지 않는다.

### 5. 초기 준비와 플레이 중 발동의 책임을 분리한다

Issue #327은 공간 요소의 종류별 상태, 점유 칸, 발견 조건, 발동 조건, 생성 근거, 지속·제거·중첩 정보를 지도 정본에 저장하고 활성화 조건을 제공한다.

칸 진입·이탈·관찰·상호작용·전투 턴 시작에 따른 실제 발동, 지속 시간 감소, 만료·제거 반영은 이동 해결 기능의 책임이다. 이는 #330의 공간 탐지·관찰·발동 구현에서 `SpatialFeatureApplicationService`를 호출해 처리한다.

따라서 #327은 발동 규칙을 저장하지 않은 상태로 끝낼 수 없지만, #327에서 별도 범용 발동 처리기를 만들지도 않는다.

### 6. 검증 경계

필수 검증은 다음 순서로 고정한다.

- 정책 단위: 종류별 상태, 지속·제거·중첩, 세 번 시도, 필수·선택 실패, 소급 생성 금지
- 계약 검증: Adventure Scenario Preparation → 내부 Combat Map 계약 → 원자적 저장 → 활성화 조건
- PostgreSQL 통합: 성공, 필수 차단, 선택 경고, 명령 재생, 지문·버전 충돌, 트랜잭션 되돌림
- 브라우저 화면부터 저장 결과까지의 통합 검증: 실제 모험 시작부터 저장·활성화까지와 필수 실패의 안전한 화면 결과

브라우저·서비스 실행 환경이 없으면 마지막 검증은 환경 차단으로 남긴다. 계약 검증 통과를 브라우저 검증 통과로 바꾸지 않는다.

## 결과

- AI는 후보만 제안하고 지도 상태를 바꾸지 않는다.
- Adventure Runtime은 준비 흐름과 활성화 조건을 소유한다.
- Combat Map은 검증된 배치 묶음과 결과를 정본으로 저장한다.
- 같은 명령의 재처리는 안전하게 재생되며, 다른 지문·오래된 버전은 거부된다.
- 준비 결과와 플레이 중 발동 결과가 같은 공간 요소 정본을 공유하지만 책임은 섞이지 않는다.
- #327 구현 blocker는 이 결정과 기존 Architecture Spec에 맞춘 후속 구현으로 해소한다.
